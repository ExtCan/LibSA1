# G64 (libsm64 in Garry's Mod): deep read, and what a "G-SA1" would need

Research date: 2026-10-06. All facts below come from reading the source of the repositories listed
in section 0 (shallow clones in the session scratchpad `scratchpad/repos/`), plus the GitHub API
(issues, commits, releases, license metadata). No third-party code is reproduced here. Identifiers,
API names, offsets and constants are quoted only where the exact value matters.

Where something is inferred rather than read directly, it is marked **(inferred)**.

---

## 0. The pieces and where they live

Upstream lineage of the native library:
`jaburns/libsm64` -> `libsm64/libsm64` (CC0) -> `Retro64Mod/libsm64-retro64` (dylanpdx; adds audio,
ROM-side model extraction, extra Mario-control functions, coordinates above 32768) -> `ckosmic/libsm64`
branch `gmod` (Retro64 changes plus G64-specific functions). The README credits Retro64 for "sound
and multiplayer".

Important caveat: **the published module source lags the released binaries.** `libsm64-gmod/main.cpp`
still has `PACKAGE_VERSION "1.0.0"` and the old PowerShell updater path (`run_updater_script`). Release
v1.0.1 (2022-09-21) says that path was replaced by the separate updater module. So the shipped
`gmcl_g64_win64.dll` was built from source that is not public.

### 1.2 Binary module (`ckosmic/libsm64-gmod`)

- Files: `g64/main.cpp` (about 1500 lines: every Lua-facing function plus module open/close),
  `g64/utils.{h,cpp}` (debug print through Lua `print`, version compare, the old PowerShell
  updater launcher, and **the hardcoded ROM texture-atlas tables**), and `g64/gamepad.{h,cpp}`
  (SDL2 GameController polling).
- Build: Visual Studio 2022 solution. `ConfigurationType=DynamicLibrary`, toolset v143, C++20 on x64
  and C++17 on Win32. `TargetName` is `gmcl_g64_win64` (x64) or `gmcl_g64_win32` (Win32). Include
  paths: `..\gmod-module-base\include` (as ExternalIncludePath), `..\libsm64\dist\include`,
  `..\SDL2-2.0.22\include`. Links `sm64.lib`, `SDL2.lib` and `SDL2main.lib`.
- CI (`.github/workflows/msbuild.yml`, windows-latest): downloads SDL2 2.0.22, then downloads the
  `libsm64` artifact produced by the `ckosmic/libsm64` `gmod`-branch workflow into `libsm64/dist`,
  then runs `msbuild /p:Configuration=Release g64.sln` and uploads `x64/Release/gmcl_g64_win64.dll`.
- GMod ABI comes only from `gmod-module-base`. `GMOD_MODULE_OPEN/CLOSE` expand to exported
  `gmod13_open(lua_State*)`/`gmod13_close`. `LUA_FUNCTION(name)` wraps a function that receives
  `GarrysMod::Lua::ILuaBase* LUA`. The `ILuaBase` virtual interface supplies stack ops, tables,
  references (`ReferenceCreate/Push/Free`), and the GMod-specific `PushVector/GetVector/PushAngle/GetAngle`.
  `SourceCompat.h` supplies a minimal `Vector`/`QAngle`. No Source SDK, no `garrysmod_common`, and no
  engine interfaces (no IMaterialSystem or IVEngineClient) are used. Everything visual goes back to Lua.

### 1.3 libsm64 fork (`ckosmic/libsm64`, branch `gmod`)

- Plain `Makefile`, gcc. Flags: `-DSM64_LIB_EXPORT -DVERSION_US -DNO_SEGMENTED_MEMORY -DGBI_FLOATS -fPIC`.
  On Windows it links `-static -lole32 -lstdc++` and outputs `dist/sm64.dll` plus `dist/include/libsm64.h`.
  `BUILD_32=1` outputs to `dist32`.
- CI (`.github/workflows/build.yml`): MSYS2 MINGW64 `make`, then `dll2lib.bat 64 dist\sm64.dll`
  (dumpbin /exports -> .def -> `lib /def`) to make an MSVC import library, then uploads `dist` as
  artifact `libsm64`. **Design point:** the C decomp code is built by gcc. Only the thin C++ module is
  MSVC, and the two meet at a C ABI DLL boundary.
- Source layout: `src/libsm64.c` (public API), `load_surfaces.c` (collision upload), `gfx_adapter.c`
  (display-list interpreter that writes triangles), `load_anim_data.c`, `load_tex_data.c`,
  `fake_interaction.c` (damage/attack without real objects), `obj_pool.c`, and `src/decomp/**`
  (trimmed SM64 decomp: `engine/`, `game/mario*.c`, `audio/`, `pc/` audio back-ends, `tools/` ROM
  parsers: `libmio0`, `n64graphics`, `geolayout_parser`, `displaylist_parser`, `convUtils` for
  sound-bank conversion). `global_state.{c,h}` plus `shim.h` turn SM64's globals into fields of a
  per-Mario `struct GlobalState` reached through a bound pointer `g_state`. That is how multiple
  independent Marios exist.

### 1.4 Naming, platforms, GMod branches

- GMod binary modules live in `garrysmod/lua/bin/` and are named `gmcl_<name>_<platform>.dll`
  (client realm) or `gmsv_<name>_<platform>.dll` (server realm). Platform suffixes in GMod's convention
  are `win32`, `win64`, `linux`, `linux64`, `osx`, `osx64`. Lua loads them with `require("<name>")`.
  G64 uses `require("g64")` -> `gmcl_g64_win64.dll` and `require("g64_updater")` ->
  `gmcl_g64_updater_win64.dll`.
- **Client-only:** there is no `gmsv_` module. The server runs pure Lua, so dedicated servers need only
  the Workshop addon. Each player who wants to be Mario needs the DLLs and a ROM.
- **Windows x64 only.** The README requires the Steam beta "x86-64 - Chromium + 64-bit binaries". The
  Lua refuses on `jit.arch == "x86"` and hardcodes `gmcl_g64_win64.dll` (the win32 line is commented
  out). Win32 project configurations exist but are not shipped. Linux and macOS are unsupported
  (issues #4, #47, #51). A user's Linux attempt (#47) compiled but crashed in `process_display_list`.
- `sm64.dll` is an implicit-link dependency of the module. Windows resolves it from the executable's
  directory, so it must sit in `GarrysMod/bin/win64/` next to `gmod.exe`, not in `lua/bin`. SDL2: the
  module links SDL2 dynamically. The installer's uninstall list does not include `SDL2.dll`, so it is
  presumably the one GMod already ships in `bin/win64` **(inferred)**.

### 1.5 Installation and distribution (why it is not Workshop-only)

- The Workshop item (id 2814638140) can only carry Lua and content. Workshop `.gma` files cannot
  contain DLLs. So the natives come from GitHub releases (`libsm64-g64-<ver>.zip`, about 1.3 MB for 1.0.1).
- `G64Installer` (Avalonia, C#) does the following:
  1. Finds Steam via registry `HKLM\SOFTWARE\Wow6432Node\Valve\Steam\InstallPath`.
  2. Scans `steamapps/libraryfolders.vdf` for `appmanifest_4000.acf` (GMod) to get the install dir. It
     validates that dir by the presence of `hl2.exe` or `gmod.exe`.
  3. Fetches `api.github.com/repos/ckosmic/g64/releases`, downloads `releases[0].assets[0]`, and
     extracts it over the GMod root.
  4. Its uninstall list shows the payload: `bin/win64/{sm64,bz2,jsoncpp,libcurl,zip,zlib1}.dll`
     and `garrysmod/lua/bin/{gmcl_g64_win64,gmcl_g64_updater_win64}.dll`.
- Auto-update (`g64_auto_update`, default 1). At `InitPostEntity`, before `require("g64")`, the Lua
  does `require("g64_updater")` and calls `g64updater.UpdateG64From(installedVersion)`. That function
  uses libcurl to read the GitHub releases JSON, compares versions, downloads the first asset to
  `./libsm64-g64.zip`, and unzips it into the CWD (the GMod root). Updating before the main module is
  loaded avoids file locks. There is **no signature or hash check** on downloaded native code
  (supply-chain risk).
- Version gating: Lua constants `REQUIRED_LIBSM64 = 3` and `REQUIRED_MODULE = 2`, `LIB_VERSION 3` in
  `libsm64.h`, and ConVar `g64_lib_version` (set from `libsm64.GetPackageVersion()`). In multiplayer,
  outdated clients are refused (Mario removed with a chat message).

## 2. How the ROM is supplied, validated, read and ripped

### 2.1 Supplying the path

- Client ConVar `g64_rompath` (archived) is set in Spawn menu -> Utilities -> G64 -> Settings. That
  panel has a `DTextEntry` and a "Browse..." button that calls `libsm64.OpenFileDialog()`.
- `OpenFileDialog` is a Win32 `GetOpenFileName` call with filter `Z64 Files (.z64)`. It returns the
  path string, or `0` on cancel or failure. On non-Windows it returns `-1`, while the Lua checks for `1`
  (a mismatch).
- `g64utils.GlobalInit()` runs lazily: when a Mario is spawned, when a coin initialises, or when the
  spawn menu opens. It reads the ConVar and calls `libsm64.GlobalInit(romPath)`.

### 2.2 Validation: there is none in code

- The README publishes MD5 `20b854b239203baf6c961b850a4a51a2` and SHA-1
  `9bef1128717f958171a4afac3ed78ee2bb4e86ce` (SM64 US, big-endian `.z64`). **Neither the module nor
  the library checks them.**
- `ReadBinaryFile` reads the whole file through an `istream_iterator` (slow but fine for 8 MB). If the
  vector is empty, `GlobalInit` returns `false` and Lua prints "Error loading ROM".
- Otherwise `sm64_global_init` immediately `malloc`s 8 MiB (0x800000) and `memcpy`s 8 MiB from the
  buffer. A wrong, short or byte-swapped (`.v64`/`.n64`) file therefore reads past the end or parses
  garbage. That causes several of the "crash when spawning Mario" issues **(inferred from code)**.

### 2.3 What is extracted, from where, and how (US ROM file offsets)

All offsets are hardcoded constants for the US ROM. Parsing happens once in `sm64_global_init` or
`GlobalInit`, entirely in memory. Nothing is written to disk.

| Asset | ROM location | Decoder / path |
|---|---|---|
| Mario animations | table at `0x004EC000` (`ANIM_DATA_ADDRESS`): u32 count, then (offset,size) pairs | `load_mario_anims_from_rom`: for each entry, read the big-endian header (flags, animYTransDivisor, startFrame, loopStart, loopEnd, unusedBoneCount, values offset, index offset, end offset) and copy the `index` (u16) and `values` (s16) arrays into native `struct Animation`. `load_mario_animation(index)` just points at entry *index* |
| Mario geometry (geo layout) | segment 0x17 maps to ROM `0x1279B0`. The root branch is `0x17002CE0` (`mario_geo_load_body`) | `initMarioGeo` builds a small wrapper geo layout in memory (shadow, z-buffer, scale 0.25, backface-culling ASM nodes) that branches to the parsed body. `geolayout_parser.c` walks the N64 geo commands (0x00 to 0x1D subset: branch, open/close node, switch case, translate/rotate, animated part, display list, shadow, held object, scale, etc.) and re-emits them as the decomp's `GeoLayout` macros. Function pointers are mapped by a hardcoded table of 13 US RAM addresses -> native callbacks (`geo_mirror_mario_backface_culling` 0x80277D6C, `geo_switch_mario_stand_run` 0x80277150, `geo_mario_head_rotation` 0x802773A4, `geo_switch_mario_eyes` 0x802771BC, `geo_switch_mario_cap_on_off`, `geo_switch_mario_hand`, `geo_mario_hand_foot_scaler`, `geo_mario_tilt_torso`, `geo_mario_rotate_wing_cap_wings`, ...) |
| Mario display lists, vertices, lights | MIO0 block at `0x114750` (decompresses to segment 0x04 data, `0x114750`-`0x1279B0`) | `displaylist_parser.c`: MIO0-decode once, then translate Fast3D commands into the library's own `gfx_adapter` command stream: `G_VTX` (16-byte big-endian `Vtx`), `G_TRI1` (indices / 10), `G_DL`, `G_ENDDL`, `G_TEXTURE`, `G_SETTILESIZE`, `G_MOVEMEM` lights (0x86 diffuse / 0x88 ambient -> `Lights1`). `G_SETTIMG` segment addresses are mapped by a hardcoded switch to **atlas slot indices 0-10** (metal, button, M logo, sideburn, mustache, eyes x4, wing halves x2). Many RDP commands become no-ops |
| Textures (5 atlases) | `SM64TextureAtlasInfo` tables hardcoded in the **module** (`utils.cpp`): Mario `0x114750` (MIO0) with 11 entries; coins `0x201410` (4x 32x32 IA16); UI `0x108A40` (14x 16x16 RGBA16: digits, x, coin, Mario head, star); health `0x201410` (11 power-meter pieces); particle `0x114750` (1x 32x32) | `sm64_texture_load(rom, atlas, out)` -> `load_textures_from_rom`: MIO0-decode the block, then convert each texture with `n64graphics` `raw2rgba`/`raw2ia` (16-bit) and blit it into an RGBA8 atlas laid out horizontally. Atlas widths: Mario 704 (11x64), coin 128, UI 224, health 704, particle 32 |
| Sound banks and music | `0x57B720` CTL (instrument banks), `0x593560` TBL (ADPCM sample data), `0x7B0860` sequences (`.m64`), `0x7CC621` bank-sets table | `convUtils.c` `parse_seqfile` reads the big-endian seq-file headers. For CTL it re-materialises instruments, drums, envelopes, samples, loops and ADPCM books as native little-endian structs into one 0x20B40-byte arena, then `ptrs_to_offsets` converts pointers back to offsets so the decomp audio loader can consume them. The bank-sets table is patched (one byte inserted at 0x45). Then `audio_init`, `sound_init`, `sound_reset(0)` |

Data flow for textures back to Lua: `GlobalInit` returns **five Lua tables**, one per atlas. Each is
a 1-based array with one entry per pixel, and each entry is a 4-element `{r,g,b,a}` table (0-255).
For the 704x64 Mario atlas that is 45,056 small tables built through the Lua C API on every init.

Contrast with upstream libsm64: there, `import-mario-geo.py` downloads `actors/mario/geo.inc.c` and
`model.inc.c` from the decomp repo at **build time**, so Mario's vertices and display lists are
compiled into the binary and only textures and animations come from the ROM. The Retro64/G64 path
instead rips **all** model data at runtime. That is the model G-SA1 must follow.

## 3. The Lua-facing module API, lifetimes, threading, per-tick flow

`GMOD_MODULE_OPEN` creates the global table `libsm64` and calls `gamepad_init()` (SDL joystick and
game-controller init, open controller 0). `GMOD_MODULE_CLOSE` calls `sm64_global_terminate()`, nils
`libsm64`, closes SDL, and possibly runs the old updater script.

Coordinate conversion helper used everywhere (S = `scaleFactor`, set by `SetScaleFactor`):
SM64 position = (-x*S, z*S, y*S) from Source (x, y, z). The reverse divides by S. Triangles are
re-wound (v3, v2, v1) because the X negation flips handedness.

### 3.2 Per-Mario lifetime and buffers

- Native side (`sm64.dll`): `obj_pool` slot holding a `MarioInstance{GlobalState*}`. The first create
  also builds the shared graph node from the parsed geo layout. Each create allocates a fake Mario
  object and an `Area` plus `Camera` stub, sets the spawn info, runs `init_mario_from_save_file` and
  `init_mario`, and (if not fake) sets `ACT_SPAWN_SPIN_AIRBORNE`. **Every API call re-binds
  `g_state`**, so calls for different Marios cannot be interleaved across threads.
- Module side: `std::map<int, mInfo>`. Each Mario gets four float arrays sized for
  `SM64_GEO_MAX_TRIANGLES = 1024` (position, normal, colour: 1024*9 floats each; uv: 1024*6), and
  **16 Lua registry references** to persistent tables plus one anim-info table. The tables are reused
  every tick to limit garbage. Layout per buffer b in {0,1}, at reference offset 8*b:
  `0` positions (Vector, Source units, **entity-local**: Mario's position is subtracted, with z-5),
  `1` normals, `2` U (multiplied by 0.6875 = 704/1024 because the render target is 1024 wide),
  `3` V, `4` colour index 1..6, `5` vertex-info table {1..5 -> the five tables above},
  `6` state table, `7` tick-result table {state, vertex info}.
- State table fields: 1 position (Source units), 2 velocity (SM64 units/frame; the axis swizzle
  is inconsistent with position), 3 facing (2*pi - faceAngle radians), 4 raw health u16
  (wedges = high byte), 5 action, 6 flags (cap bits 0x2 vanish, 0x4 metal, 0x8 wing), 7 particle
  flags, 8 invincTimer, 9 hurtCounter, 10 numLives, 11 holdingObject, 12 dropMethod.
- Colour trick: during the first two ticks the module records the first 6 distinct diffuse-light
  colours it sees into a **global** `marioColorLUT`. After that each vertex is emitted as an index into
  that LUT, and Lua replaces the indices with the user's 6 configurable colours (overalls, shirt/hat,
  skin, hair, gloves, shoes).
- Deletion: `sm64_mario_delete` frees the instance. The module frees its `new[]` arrays with `free()`
  (mismatched) and releases its references.

### 3.3 Threading

- Everything is called on the GMod **client main (Lua) thread**, from `Think`, `CalcView`,
  `PostDrawOpaqueRenderables` and the tick timer.
- `sm64_global_init` starts one **pthread** (winpthreads, statically linked). It loops every about
  33 ms: `audio_signal_game_loop_tick()`, then synthesises 2x544 or 2x528 stereo s16 samples at
  32 kHz and pushes them to WASAPI (or PulseAudio/ALSA on Linux, or a null backend). There is no
  locking between this thread and main-thread `play_sound` or `play_music` calls. It is cancelled
  with `pthread_cancel` on terminate.

### 3.4 Per-tick flow (local player)

1. **Clock.** `systimetimers` (a `Think`-driven SysTime timer) fires `hook.Call("G64GameTick")` every
   `G64_TICKRATE = 1/33 s / host_timescale`. It fires **at most once per frame** with no catch-up.
   Below 33 FPS Mario runs in slow motion, and the timer drifts because LastRun = now.
2. `G64_UPDATE_COLLISION`: move every tracked prop's surface objects, add up to 8 queued props, move
   NPC and player colliders, and react to `host_timescale` or `g64_scale_factor` changes (a scale change
   rebuilds all prop collisions).
3. `G64_MARIO_TICK` -> `MarioTick` (local closure):
   1. Inputs: the keyboard ConVars become a stick vector normalised in Lua; A, B, Z come from the
      jump, attack and duck binds; the pickup bind also sets B. Facing is `LocalPlayer():GetAimVector()`,
      or the gmod camera entity's direction.
   2. Swap the result tables, then call `libsm64.MarioTick(id, bufferIndex, facing, stick, A, B, Z)`.
   3. In C: `update_button` builds pressed/down masks. Camera yaw is `atan2s(camLookZ, camLookX)`;
      `stickX = -64*x`, `stickY = 64*y`. Then `apply_mario_platform_displacement`, `bhv_mario_update`
      (the full action state machine and physics steps), `resolve_object_collisions`,
      `update_mario_platform`. Then the geo graph is processed through `gfx_adapter` into triangles,
      and the health-wedge refill sound plays if needed.
   4. `GetMarioAnimInfo` returns the animation state.
   5. Lua reads the state table; reloads the static-surface chunk if Mario left it; spawns particles
      from particle flags; runs ground and air attack traces; applies pending caps; handles death and
      respawn; spawns bubble particles; flips `bufferIndex`.
   6. `net` `G64_TRANSMITMOVE` to the server (see 6.5).
4. Every frame (`ENT:Think`): `GenerateMesh()` rebuilds the IMesh, interpolating from the previous to
   the newest buffer with t = (SysTime - lastTick)/tickrate. That is one tick of display latency.
   `VehicleTick` -> `FindWaterLevel` -> `SetMarioWaterLevel`. Held-object update.
5. `CalcView`: interpolate the position, `SetPos`/`SetNetworkOrigin` the SENT (so other systems see
   Mario where he is drawn), then compute the third-person camera.

## 4. World collision: GMod geometry -> libsm64 surfaces

### 4.1 Static world

libsm64 has **no spatial partitioning**. `find_floor`, `find_ceil` and `find_wall_collisions` scan every
static surface and every surface-object surface linearly. G64 works around this by loading only the
geometry near Mario.

Pipeline (first visit to a map):

1. Client `InitPostEntity` -> `InitializeWorld(2)`. After a 2 s timeout the client sends
   `G64_UPLOADCOLORS` and `G64_LOADMAPGEO`.
2. **Server** (`LoadMapGeometry`): `Entity(0):GetPhysicsObject():GetMeshConvexes()` gives the world
   brush collision hull as triangle-vertex lists. Header message type 0 sends world min/max (int16
   x6) from `Entity(0):GetModelBounds()`. Then a per-player `Tick` hook sends **32 convexes per tick**,
   each as its own message type 1 (u32 count + int16 xyz per vertex). Type 2 means done. Volume
   tuning here fixed "overflowed reliable channel" kicks (#53).
3. **Client** bins every triangle into a 2-D XY grid. World grid: **1000x1000-unit** cells, sized from
   world bounds. Displacements: a separate **500x500** grid. A triangle goes into every cell its XY
   bounding box touches, with a +/-100-unit margin. Cells store flat vertex lists.
4. Displacements are not in the world physics mesh, so the client **parses the .bsp itself** with
   luabsp (coroutine-sliced): `LUMP_DISPINFO` (26), `LUMP_DISP_VERTS` (33), plus faces, edges and
   vertices for the base quads, to build displacement triangles. This is skipped on old BSP versions
   (TF2), and controlled by `g64_process_displacements`.
5. Static props are not in the world physics mesh either. luabsp reads the `sprp` game lump. For each
   model name the client creates a temporary `ents.CreateClientProp` to read its physics convexes, then
   rotates them with a yaw/pitch/roll matrix and translates by the prop origin. Only `Solid == 6`
   (VPHYSICS) props are used. Controlled by `g64_process_static_props`.
6. The cache is written to `data/g64/cache/<map>_cache.dat` (binary, version `MAP_GEO_CACHE_VERSION = 1`):
   u32 version; int16 xDelta, yDelta; int16 worldMin xyz; int16 worldMax xyz; u16 xChunks, yChunks,
   xDispChunks, yDispChunks; then for every world cell (x-major) u32 vertexCount and float xyz each;
   then the same for displacement cells. Later visits load it in C++ (`LoadMapCache`). The author
   reports 30-45 s first-time init on gm_fork and about 1 s from cache.
7. At runtime: whenever Mario's world or displacement cell changes, `StaticSurfacesLoad(cellVerts,
   dispCellVerts)` replaces **all** static surfaces with that one cell plus that one displacement cell.

Consequences:
- Each surface gets type 0 (default) and terrain 0. Footstep and terrain sound is fixed per tick
  instead: a downward trace reads `MatType`, which maps to SM64 terrain (stone, grass, snow, sand,
  water, spooky/wood) and surface (default or noise-default), sent via `SetMarioFloorOverrides`.
- Thin and transparent geometry (fences, glass, playerclip, `func_breakable_surf`) is missing because
  only physics hulls are used. See issues #8, #26, #44.

### 4.2 Dynamic objects

- **Props and brush entities** (whitelists `AllowedEnts`: prop_physics/dynamic/vehicles/doors/simfphys;
  `AllowedBrushEnts`: func_door, func_movelinear, func_tracktrain, func_brush, func_breakable,
  func_rotating, and others). On `OnEntityCreated` they are queued, and at most 8 are processed per tick:
  - Scripted entities with physics: one surface object **per physics convex**.
  - Brush entities: `GetBrushSurfaces()`, fan-triangulated into one surface object.
  - Other props: a temporary client `PhysicsInit(SOLID_VPHYSICS)` to read convexes (one object per
    convex), falling back to `util.GetModelMeshes` render triangles. Then `PhysicsDestroy`.
- Every tick each surface object gets `SurfaceObjectMove(id, ent:GetPos(), ent:GetAngles())`.
  libsm64 re-transforms all of its triangles, and stores the position and angle delta as velocity so
  `apply_mario_platform_displacement` carries Mario on moving platforms.
- To disable collision without reallocating, G64 moves the object to (0, 0, -32768). This happens for
  collision group world, no-collide, the player's own vehicle, the vanish cap, the held prop,
  `IsSolid() == false`, and brush `Solidity` keyvalue 0 (polled server-side every 1 s and networked).
- Per-prop SM64 surface and terrain types can be set with the toolgun `g64surfacechanger` (networked
  `G64_CHANGESURFACEINFO`, stored as a duplicator modifier). Examples are quicksand, wind and noise.
- **NPCs and other players**: `ObjectCreate(pos, AABB height, AABB x-extent)` cylinders, moved every
  tick (dead players are parked far away). SM64 pushes Mario out of them.
- **Rotation is wrong in some orientations** (issue #5, still open). GMod `Angle` (pitch, yaw, roll) is
  remapped to SM64 Euler, and libsm64 rebuilds it with `mtxf_rotate_zxy_and_translate`. The rotation
  orders do not match, and past 90 degrees of pitch the result mirrors. The commit "failed rotation fix
  attempts" exists. The lesson for G-SA1 is to pass **matrices or quaternions**, not Euler angles.

### 4.3 Scale

- `g64_scale_factor` (replicated, cheat, default 2.5, range 0.1-8): **1 Source unit = 2.5 SM64 units**.
  Mario's 160-unit hitbox therefore becomes 64 HU, close to a player's 72 HU. The SENT render bounds
  are +/-160/S.
- Coordinates travel as int16 Source units over the network and in the cache header. Source maps are
  within +/-16384, which becomes +/-40960 SM64 units. That exceeds s16, so the fork's 32-bit surface
  vertices (`Vec3i`, s32 lowerY/upperY) and removed level-boundary checks are required.

### 4.4 Performance strategies used (and how well they worked)

- Spatial chunking with replace-on-cell-change, as above. Large triangles are duplicated into many cells.
- On-disk cache, loaded in C++.
- Coroutines for BSP parsing, and network streaming throttled to 32 convexes per tick.
- Prop queue (8 per tick). Parking objects instead of deleting them. The solidity poll was moved from
  per tick to a 1 s timer (fix for #75).
- Still reported: FPS cost even when Mario is not spawned (#75, #76, #111) and multi-minute first loads
  on big maps (#41).

## 5. Rendering

- **Mesh generation is in Lua, every frame.** The module writes the up to 3072 vertices of the tick
  into persistent Lua tables (5 table writes per vertex, through the C API). `ENT:GenerateMesh()`
  destroys and recreates `self.Mesh = Mesh()` every `Think`, then runs
  `mesh.Begin(MATERIAL_TRIANGLES, n)` with `mesh.Position`/`Normal`/`TexCoord`/`Color`/`AdvanceVertex`
  per vertex, optionally `LerpVector`-interpolating position and normal between the two buffers
  (ConVar `g64_interpolation`).
- **Interpolation is per vertex**, not per bone. That causes "Mario becomes 2D on a quick 180" (#19):
  vertices pass through the centre. The author's answer was to disable interpolation.
- Wing cap: when the wing cap is on and the vertex count exceeds 2256, the **last 24 vertices** are
  treated as the wings and built into a second mesh (alpha-tested, `$nocull`). This depends on
  display-list order. #130 reports `mesh.Begin` with 0 triangles.
- Materials (`CreateMaterial` at load):
  - `MarioLightingMat`: VertexLitGeneric on `vgui/white`, for Source lighting and flashlight.
  - `MarioVertsMat`: UnlitGeneric with `$vertexcolor`.
  - `MarioTexMat`: VertexLitGeneric on the RT, with `$decal` and `$translucent`.
  - `MarioWingsMat`: alpha-test, no-cull.
  - Metal cap: `debug/env_cubemap_model`.
  - Coin, UI, health and particle/bubble UnlitGeneric materials on their RTs.
- Draw: `ENT:GetRenderMesh()` returns the mesh, then `DrawEither()` does three `DrawModel()` passes
  with `render.MaterialOverride`:
  1. Lit white.
  2. Vertex colour, multiplied in with `OverrideBlend(DST_COLOR, ZERO)`.
  3. Textured decal (texture alpha masks the eyes, logo and buttons over the vertex colours).
  The metal cap replaces passes 2-3 with a multiplied cubemap. During invincibility frames Mario
  blinks by skipping alternate buffers.
- Vanish cap: a stencil silhouette for the local player, plus a screen-sized RT composite. The
  framebuffer is copied after opaques, a "Mario mask" RT is filled, and they are blended in
  `PostDrawTranslucentRenderables` for translucency.
- **Texture upload from ROM data.** GLua cannot create a texture from bytes. The Lua therefore makes
  RTs with `GetRenderTargetEx` (`Mario_Texture` 1024x64, `Coin_Texture` 128x32, `UI_Texture` 256x16,
  `Health_Texture` 1024x64, `Particle_Texture` 256x32; RGBA8888, no depth). It then **draws every
  pixel as a 1x1 `surface.DrawRect`** inside `cam.Start2D`. That is about 45 k draw calls for Mario.
  RTs are lost on `mat_reload`, alt-tab or resolution change. A 1 s timer reads pixel (44, 8) of the
  Mario RT with `render.CapturePixels`/`ReadPixel` and redraws if it is black. The
  `OnScreenSizeChanged` hook also redraws. UV fudge factors (+0.002, x0.9968, +0.25/32 on coins)
  compensate for sampling and centring.
- LOD: none. Mario is always the full model (about 750 triangles).
- Shadow: the server sets the SENT's model to `models/hunter/misc/sphere075x075.mdl` so Source's render
  -to-texture shadow gives a round blob. The client never draws the model itself.
- HUD (`g64_hud.lua`): an SM64-style power meter from the health atlas (background halves plus wedge
  sprite per health), lives with the Mario head, coins and star counter from the UI atlas, all drawn
  with `surface.DrawTexturedRectUV`. Default GMod health and crosshair HUD elements are hidden.
- Coins are camera-facing 3D2D sprites from the coin atlas, animated through 4 frames at 10 Hz. Caps
  use stock GMod models (top hat), not ROM models.
- Camera: `CalcView`, based on `drive_base`'s third-person hull trace. Distance is `g64_cam_distance`
  (mouse wheel, 0-3000) / S; **0 means first person**, with eye height lerped down while crouching
  (action flag 0x8000). Mario's own mesh is hidden in first person unless a camera entity is in use.
  `gmod_cameraprop` overrides are honoured through the server-networked `UsingCamera` entity. Vehicles
  use the vehicle's own third-person view. The gamepad right stick feeds `InputMouseApply`.

## 6. Gameplay integration

### 6.1 Possession model

- Spawning `g64_mario` (server SENT, owner = player): the server calls
  `drive.PlayerStartDriving(ply, mario, "G64_DRIVE")`, sets `OBS_MODE_CHASE`, removes weapons, sets max
  health 8, and spawns a server-side `g64_physbox` (32x32x60 bbox that follows Mario). The physbox
  exists so that **triggers** see Mario.
- `trigger_teleport` brushes are mirrored at map start into `g64_tptrigger` entities. On touch by the
  physbox they send `G64_TELEPORTMARIO` to the owner, whose client calls `SetMarioPosition`/`SetMarioAngle`.
- Exactly one Mario per player. The player model is hidden and scaled to 0.8.
- Removal: the R key (`g64_remove`), undo, death, disconnect, or a game over (respawns at an
  `info_player_start` if `g64_respawn_mario_on_death`).

### 6.2 Input

- Keyboard binds are client ConVars: `g64_forward/back/moveleft/moveright` (stick), `g64_jump` (A),
  `g64_attack` (B), `g64_duck` (Z), `g64_pickup` (B plus pickup mode), `g64_remove`, `g64_emotemenu`,
  `g64_freemove` (`ACT_DEBUG_FREE_MOVE`, needs `sv_cheats`).
- Input is blocked while chat, the spawn menu or the game UI is open.
- Gamepad comes from SDL2 inside the module: left stick with an 8000 deadzone, A, X as B, RT > 0.75 as
  Z, right stick for the camera. In vehicles, pad buttons are translated into `CreateMove` buttons.
- The camera direction comes from the player's aim vector. That vector is the SM64 "camera yaw", so
  stick input is camera-relative as in the original game.

### 6.3 Health, damage, combat, items

- **Incoming damage.** Server `EntityTakeDamage` on a Mario player cancels Source damage and sends
  `G64_DAMAGEMARIO` (damage/10 rounded up, source position) to the client, which calls
  `MarioTakeDamage` (SM64 knockback). The client sends health wedges (4 bits) back in every move
  packet, and the server mirrors them with `ply:SetHealth`. Health kits and vials map to `MarioHeal(4)`
  and `MarioHeal(2)`.
- **Outgoing attacks are client-side traces.**
  - Ground attacks (punch, kick, trip, dive, slide kick): a `TraceHull` forward 90/S units.
  - Air attacks: a `TraceHull` 150/S units downward (stomp / ground pound).
  - On NPCs and players, `MarioAttack` (SM64 bounce) is called and then `G64_DAMAGEENTITY` goes to the
    server. The server applies `DamageInfo` (random min..min+10, force) and spawns a yellow coin (NPC)
    or blue coin (player) on kill.
  - On props the server applies physics force, or the client starts `ACT_PICKING_UP` for small props
    (volume < 65000 and whitelisted). The server then moves, freezes or throws the held prop through
    `G64_UPDATEHELDOBJECT`.
  - A per-entity `HitStunTimer` (0.25 s) prevents repeated hits.
- **Items.** Coins (yellow 1, red 2, blue 5), 1-ups and caps are SENTs. **Collection is detected on
  the client** (distance < 40 HU), which tells the server to remove the item. That is client-
  authoritative and cheatable. Coins heal Mario; for non-Mario players they give +25 HP or armour.
- **Caps.** `MarioEnableCap(id, flag, timer from g64_{wing,metal,vanish}cap_timer ConVar, playMusic)`
  sets the flag, starts the put-on-cap action if idle, plays star and voice sounds, and plays cap music
  if enabled. Vanish cap also: props are parked so Mario passes through them, bullets pass through
  (server `SetNotSolid` from the flags in move packets), and the camera mask changes.
- **Water.** Per frame, client traces with `MASK_WATER` (up 10000 and down) find the surface Z, which
  goes to `SetMarioWaterLevel`. libsm64's own `find_water_level` always returns -100000.
- **Emotes.** A radial menu calls `SetMarioAction` with cosmetic actions (sleep, cough, bonk,
  throw, ...).
- **Vehicles.** The SENT is parented to the vehicle seat, and Mario is forced into
  `ACT_HOLD_BUTT_SLIDE_NO_CANCEL` with his position pinned to the player.

### 6.4 Audio

- **All SM64 audio is synthesised inside `sm64.dll`** by the decomp sequence player and synthesis from
  the ROM banks, and output straight to the OS through WASAPI (32 kHz stereo). GMod's sound system is
  not involved.
  - Consequences: no 3D positioning (Mario's `cameraToObject` is zeroed, so everything is centred), no
    Source DSP or occlusion, and the volume is separate (`g64_global_volume` -> `SetGlobalVolume`).
    Reverb is a global `SetGlobalReverb`; the `dsp_automatic` hookup is commented out.
  - Very loud by default (#34). Remote Marios are silent, because the anim-only path does not run the
    action code that triggers sounds **(inferred from code)**.
- Mario's voice clips, footsteps and action SFX are triggered by the decomp action code itself.
- Lua adds coin, red-coin, 1-up, hit and pound sounds with `PlaySoundGlobal(GetSoundArg({bank,
  playFlags, id, priority, flags2}))`; the table of tuples is in `g64_types.SM64SoundTable`. Cap music
  uses `PlayMusic(0, (priority<<8)|seqId, 0)`; all music players are stopped on removal.

### 6.5 Networking and multiplayer

- **Model:** each client simulates only its own Mario (client-authoritative position and health).
  Other players' Marios are rendered locally as **"fake" libsm64 instances driven only by animation
  state.**
- Local -> server, every tick (about 30 Hz), reliable `G64_TRANSMITMOVE`: position as int16 xyz
  (Source units), animID int16, animAccel int32, gfx rotation 3x int16, health 4 bits, flags u32.
  That is about 22 bytes of payload.
- The server sets `ply:SetPos` and `mario:SetPos` to the networked position, mirrors health and
  vanish-cap non-solidity, and relays `G64_TICKREMOTEMARIO` (entity, anim id, accel, rotation, flags) to
  every other player **whose view cone contains the position** (angle from crosshair < FOV). That is a
  crude interest filter.
- Remote clients store the latest anim state. On their own `G64GameTick` they call
  `MarioAnimTick(animInfo, id, buf, flags, offset)` at the owner's networked position, double-buffer
  for interpolation only if the frame rate is above 33, and hide the remote Mario if no update arrived
  for 1.5 s. There is **no extrapolation or prediction** beyond that. The animation frame is not sent,
  so remote animation phase drifts (each client advances it locally).
- Colours: `G64_TRANSMITCOLORS`/`G64_UPLOADCOLORS` go to the server, which stores them per player and
  broadcasts `G64_UPDATEREMOTECOLORS`. Late joiners use `G64_REQUESTCOLORS`.
- Map geometry is streamed from the server per client (4.1). This is the only use of the server's
  privileged physics mesh.
- All 26 net strings: `LOADMAPGEO, PLAYERREADY, HURTNPC, USEENTITY, DAMAGEENTITY, TRANSMITMOVE,
  TRANSMITCAP, DAMAGEMARIO, INITLOCALCLIENT, TICKREMOTEMARIO, TRANSMITCOLORS, UPDATEREMOTECOLORS,
  UPDATEREMOTECAP, REQUESTCOLORS, UPLOADCOLORS, REMOVEINVALIDMARIO, CHANGESURFACEINFO,
  RESETINVALIDPLAYER, SPAWNMARIOATPLAYER, REMOVEFROMCLIENT, RESPAWNMARIO, COLLECTED1UP, COLLECTEDCOIN,
  SPAWNNEWPLAYER, UPDATEHELDOBJECT, TELEPORTMARIO`, all with the `G64_` prefix.
- Level transitions: on `InitPostEntity`, if a Mario owned by the local player survived the changelevel,
  the client resets it and asks the server to respawn Mario after map geometry is ready
  (`G64_SPAWNMARIOATPLAYER`).

### 6.6 Saving and persistence

- `data/g64/config.json`: Mario colours, as JSON with default-merging.
- `data/g64/cache/<map>_cache.dat`: collision cache (4.1). Command `g64_purge_map_cache` deletes it;
  `g64_disable_cache` skips it (a workaround for #111).
- Client ConVars (archived): ROM path, keybinds, volume, HUD scale, camera distance, interpolation,
  emote list, auto-update.
- **No SM64 save file.** `gCurrSaveFileNum = 1` and the save functions are stubs. Lives and coins live
  only in Lua and reset on map change.

## 7. Pain points, known issues, design decisions

From 130 issues/PRs (83 open) and the commit history (author ckosmic, active 2022-04 to 2023-03; the
project is effectively unmaintained since then):

1. **Install friction dominates the issue tracker** (#1, #22, #43, #83, #85, #104, #109, #113, #119,
   #120, #125, ...). Causes: 32-bit GMod, DLLs in the wrong folder, a missing `sm64.dll` next to
   `gmod.exe`, a wrong or byte-swapped ROM, and Workshop Lua updated out of sync with the native
   package (#56: Lua called a function the installed module did not have). Hence the installer,
   auto-updater and version checks.
2. **Platform lock-in:** Windows x64 only. A Linux port attempt crashed in the display-list
   interpreter (#47); macOS is unsupported (#51, #96: file dialog).
3. **Performance:** Lua-side per-vertex marshalling and per-frame mesh rebuild, per-pixel RT painting,
   hooks running when Mario is not spawned (#75, #76), slow first map parse (#41), and a
   "cache overflowed" crash on some maps (#111).
4. **Collision fidelity:** Euler rotation mismatch (#5); missing thin, clip and glass brushes (#8, #26,
   #44); falling through Portal elevators (#42); crawlspace problems (#13, the same as in Retro64);
   the crouch hull does not shrink (#40); a one-cell window means geometry just outside the cell does
   not exist.
5. **Visual artifacts:** vertex interpolation (#19), deformation after alt-tab (#20, fixed by pausing
   interpolation while the overlay is open), the low-resolution UV glitch (#88), the wing-cap mesh
   hack (#130), and camera bugs (#62, #78, #117: camera flies upward when the world init failed).
6. **Multiplayer:** client authority, reliable messages for 30 Hz state, no animation-frame sync, and
   a crude FOV-based interest filter. Friends see a sphere (the shadow model) when they lack the module
   or ROM (#23, #93).
7. **Security and robustness:** unsigned auto-updates of native code; no ROM validation; an 8 MiB
   `memcpy` regardless of file size; no locking for the audio thread; mismatched `new[]`/`free`; and a
   leftover `system("calc.exe")` in the old updater path of `utils.cpp`.
8. Notable design decisions that worked: keep the decomp in C behind a tiny C ABI and keep GMod glue in
   a separate C++ module; rip everything from the user's ROM at runtime; cache derived (non-ROM) map
   data on disk; give each instance its own global state (`g_state`); run remote characters as
   animation-only puppets; and use the SENT plus drive system plus physbox so the rest of GMod (triggers,
   damage, vehicles, cameras) interoperates.
9. **Licensing:** the G64 repos have no license (default copyright). libsm64 upstream and the SM64
   decomp are CC0. Bundled luabsp is GPL-3.0, which is arguably incompatible with an unlicensed addon.
   No Nintendo data is distributed: it all comes from the user's ROM. Mario's model data is parsed from
   the ROM, unlike upstream libsm64, which compiles it in.

## 8. What an equivalent "G-SA1" needs, point by point

The target is a library built from this project's decompiled SA1 engine, physics and character code,
compiled for PC, and driven by a GMod module plus Lua addon. It must read the user's own GDI at
runtime; no SEGA data may ship. Each point below states what G64 did, then what G-SA1 should do.

### 8.1 Product structure (same split as G64, with fixes)

1. **`libsa1` (C, C ABI, static library or DLL)**: the decompiled SA1 code (player physics, collision,
   motion/animation, character action state machines, minimal object interactions), plus PC shims
   (memory, math, Ninja and Kamui stubs) and a disc and asset loader. It must be 64-bit clean (8.2).
2. **`gmcl_gsa1_win64.dll`** (C++, `gmod-module-base` headers). Link `libsa1` **statically** into the
   module so that only `garrysmod/lua/bin/` is touched. That avoids G64's `bin/win64/sm64.dll`
   placement problem. Optional builds: `gmcl_gsa1_win32.dll` for the default 32-bit branch, and
   `gmcl_gsa1_linux64.dll`.
3. **Lua addon** (Workshop-legal: Lua plus original art only). The server side is pure Lua, so
   dedicated servers need no binaries. This matches G64.
4. Distribution of the DLL: GitHub releases plus manual copy, or an installer. If auto-updating,
   verify a signature or hash pinned in the Lua addon, which G64 did not do.

### 8.2 Disc input (G64's ROM step, adapted to a GDI)

- ConVar `gsa1_gdipath` plus a Win32 file dialog filtered to `*.gdi` (G64's `OpenFileDialog`
  pattern), and also accept a typed path. Never send the path or any disc bytes over the network.
- Reader, ported from this repo's `tools/extract_gdi.py`:
  1. Parse the `.gdi` text: track count, then per track LBA, type (4 = data), sector size
     (2352 or 2048), file name and offset, with track files resolved relative to the `.gdi`.
  2. Use the last data track (high-density area, LBA 45000). For raw 2352-byte sectors, user data is
     bytes 16..2064.
  3. Walk ISO9660 from the PVD.
  4. Read files **lazily by path** (`1ST_READ.BIN`, `SONICADV/*.PRS`, `*.PVR`, `*.MLT`, `*.ADX`,
     `*.AFS`). Do not extract the disc to disk.
- **Validate** (G64 did not): SHA-1 of `1ST_READ.BIN` must equal
  `e74c849806db103aa87f84e41a382873bc96b6df` (US v1.005, 6,735,488 bytes; re-verified against
  `baserom/1ST_READ.BIN`). Optionally also check `IP.BIN` product and version (MK-51000, V1.005), and
  per-file hashes for the PRS/PVM files used. On mismatch, show a clear message (G64's top support
  burden was wrong inputs). Check every size and offset before parsing; no blind `memcpy`.
- Decoders needed in C/C++ (all little-endian, unlike N64):
  - **PRS** decompression (this repo has a bit-exact codec in `tools/prs.py`).
  - **PVM/PVR** textures: twiddled and VQ, ARGB1555/RGB565/ARGB4444, palettised (PVP), mipmaps.
  - **Ninja** basic models (`NJS_OBJECT`/`NJS_MODEL`/`NJS_MATERIAL`/mesh sets) and, if used, chunk
    models.
  - **NJS_MOTION** (keyframe arrays; angles in BAMS).
  - Action lists and weld data.
  - The physics parameter block.
  - Audio: MLT (AICA ADPCM/PCM sample banks) and ADX (CRI ADPCM). AFS archives if voices live there.
- **Asset addresses are fixed per build**, as G64's are. Since only one build is supported (US v1.005,
  SHA-1 checked), hardcode file offsets, preferably generated from this repo's symbol and SA Tools
  research rather than hand-typed. Spot-checked examples:
  - Sonic's physics block is at 1ST_READ file offset `0x1ADFE4` (`[Sonic Physics Data]` in
    `AdventureRip/1st_read_data.ini`). It starts with int 60 (`jump2_timer`), then floats 2.0, 16.0,
    16.0, 3.0, 0.6, 1.66 (`pos_error`, `lim_h_spd`, `lim_v_spd`, `max_x_spd`, `max_psh_spd`,
    `jmp_y_spd`), matching `figure/sonic/Physics.ini`. The other characters' blocks are listed in the
    same ini.
  - Sonic's root `NJS_OBJECT` (`s_kihon10_sonic`) is at file offset `0x1BE76C`: evalflags 0xF, no
    model, child pointer `0x8C1CE738`, which is file offset `0x1BE738`. The same ini lists its
    animations (`s_wait0`, `s_walk0`, `s_run0`, ...) and texture name `SONIC`. See also
    `figure/sonic/WeldData.ini` and `ActionList.ini`.
  - Character textures: `SONICADV/SONIC.PRS` PRS-decompresses to a `PVMH` archive of 108,000 bytes
    whose header count field reads 0x1C (28 textures). `KNUCKLES.PRS` and `E102.PRS` are also PVMs.
  - SA1 pointers in 1ST_READ are RAM addresses: file offset = ptr - `0x8C010000`. Overlay data uses its
    own load bases (`docs/layout.md`).
- **Pointer re-materialisation is mandatory.** As G64 converted N64 big-endian structs into native
  structs (CTL banks, `Vtx`, `Animation`), G-SA1 must convert 32-bit-pointer SH-4 structures (Ninja
  objects, motions, action tables) into native **64-bit** structs. Struct layouts from the game
  cannot be used in place on x64.

### 8.3 Engine scope to decompile and port (the "libsm64 core" equivalent)

- Must have:
  - The player task and action state machine for each playable character: Sonic, Tails, Knuckles,
    Amy, Gamma and Big.
  - The physics parameter use: speeds, accelerations, gravity, friction, slope handling.
  - Ground and air movement, jump, spin dash, homing attack, light-speed dash, Tails flight, Knuckles
    glide/climb/dig, Amy hammer, Gamma lock-on and shoot, Big rod. Damage and knockback, death.
  - **The player collision routines**: floor and wall shape casts against land collision, slopes and
    stairs, water, surface flags, moving-platform attachment.
  - The motion/animation player (Ninja motion interpolation, action blending, weld/morph of vertices
    between body parts, as listed in WeldData).
- Isolate all globals per instance, as libsm64's `GlobalState` plus `g_state` re-binding did, so
  several characters (local player plus remote puppets) can exist. Decide early whether the decomp
  keeps the original globals and swaps a context struct in and out, or refactors to explicit context.
- Fixed timestep: G64's "at most one tick per frame" timer caused slow motion below 33 FPS. Use an
  accumulator at SA1's native logic rate. Confirm in the decomp whether gameplay logic is per vsync
  (60 Hz) or 30 Hz, and how frame skipping is handled.
- SH-4 numeric behaviour: single-precision math, `fsca`/`fsrra` approximations and BAMS angle tables.
  Exact match is not required for a port, but keep BAMS (16-bit angle) semantics so the physics feel
  right.

### 8.4 Collision bridge GMod -> SA1 (improve on G64)

- Same sources as G64: the world physics mesh from the server, displacements and static props from
  the BSP, prop physics convexes, brush-entity surfaces.
- Do the BSP parsing **in C++** (G64 used luabsp in Lua, which was slow and GPL).
- Keep the on-disk cache, which is derived from map data, not SEGA data.
- Inside `libsa1`, replace G64's "load one 1000x1000 cell" with a real **spatial index** (uniform grid
  or BVH over all triangles). SA1's own land-collision lookup is list or bounding-sphere based; adapt it
  to query the index.
- Surface attributes: map Source `MatType`/surfaceprop to SA1 surface flags. Examples: water for
  `MAT_SLOSH`/water brushes, a slippery flag for ice, no-climb for glass. Expose a per-prop override
  tool like G64's surface changer.
- Dynamic objects: API equivalent to `surface_object_create/move/delete` taking a **4x4 matrix**
  (fixes #5). Velocities come from deltas so platforms carry the player. Disable collision with a flag
  rather than teleporting objects to -32768.
- Characters, NPCs and players: cylinder or sphere colliders, plus homing-attack target registration
  (the library needs a list of targetable positions and an id to report hits).
- **Units:** SA1 Physics.ini gives Sonic `rad=4`, `height=10` (collision units), while GMod's player
  hull is 32x32x72 HU. A starting scale of about 4-5 HU per SA1 unit would roughly match a 72 HU player
  height to Sonic's visual height. Calibrate from the model bounding box and make it a ConVar, as
  G64's `g64_scale_factor`. Axis mapping: Ninja/SA1 world space is Y-up, while Source is Z-up. Swap Y
  and Z, then check handedness (verify) and re-wind triangles if it flips, as G64 did.

### 8.5 Rendering (avoid G64's Lua bottlenecks)

- Decode the character model once into per-bone static vertex buffers plus the skeleton hierarchy
  (`NJS_OBJECT` tree). Each tick, compute bone matrices (and weld vertices) in C++.
- Preferred: build the final mesh in **C++** and hand Lua a single userdata, or create the `IMesh`
  natively through engine interfaces (`garrysmod_common`/Source SDK `IMaterialSystem` and
  `CMeshBuilder`, at the cost of more fragile headers). Minimum: return one flat packed string or
  buffer per tick instead of thousands of table writes.
- **Interpolate bones** (quaternion slerp plus translation lerp) between ticks, not vertices. That
  avoids G64's "2D on 180" artifact.
- Textures: decode PVM -> RGBA8 in C++. G64's per-pixel `DrawRect` into an RT is slow and RTs get
  cleared. Options:
  - Create textures natively (`ITexture` with a regenerator via the material system).
  - Write a PNG or VTF into `data/gsa1/cache/` and load it with `Material("../data/...")`. This keeps
    a ripped asset on the user's disk. That is local and derived from their own disc, but decide
    whether that is acceptable.
  - Keep the RT approach but upload through a faster path, and handle the RT-cleared case as G64 does.
- SA1 materials: diffuse colour, alpha, and an environment-map flag (used for shiny parts, e.g.
  Gamma, Metal Sonic) map to VertexLitGeneric plus `$envmap`. Support multiple textures per model (not
  an 11-slot atlas): one material per texture id.
- Character extras: Sonic's spin-ball model (`s_spin0`, a separate model), Super Sonic if wanted, and
  effect models such as the homing attack trail and spin dash dust (from the effect PRS files, or
  original particles as G64 did).
- HUD: rings, lives, timer from the HUD texture PVMs on the disc. Rings are SA1's health, so the HUD
  matters for gameplay. Pick their PVR/PVM files from the disc listing **(to identify)**.

### 8.6 Gameplay integration

- Possession: copy G64's pattern: a SENT, the drive system, `OBS_MODE_CHASE`, a server physbox for
  triggers, and a teleport mirror. It works and interoperates with GMod.
- Input: keyboard binds plus gamepad. G64 bundled SDL2; G-SA1 could instead read GMod's own
  `input.*` joystick ConVars to avoid a second gamepad stack. SA1 needs more buttons than SM64 (A jump,
  B/X action, Y, L/R camera, analog triggers for some actions); expose a richer input struct than
  libsm64's 3 buttons.
- Camera: GMod-side third person as in G64 (camera-relative stick). SA1's own camera code is
  optional; it would need level camera data that GMod maps do not have.
- Health: ring count. On damage, scatter rings (as GMod entities) and give invincibility frames; with
  zero rings, death. Map incoming Source damage to "hit" events, as `G64_DAMAGEMARIO` did, and send
  outgoing attacks (homing attack, spin, hammer, Gamma shots) as server-validated damage requests.
- Items: rings, 1-ups, shields and speed shoes as SENTs. Make collection **server-side** (G64's
  client-side pickup is cheatable).
- Audio:
  - SA1 SFX come from MLT banks (AICA ADPCM) and voices from ADX/AFS; music is ADX.
  - Simplest faithful path: decode samples in C++ and mix with miniaudio or WASAPI inside the module,
    as G64 did. To do better than G64, pass the listener position each frame and do 3D panning and
    attenuation, honour a volume ConVar, and let remote characters' sounds play (send sound events in
    the network state).
  - Alternative: decode to WAV in `data/` and use GMod's `sound.PlayFile`/`EmitSound` for real 3D audio
    and Source DSP, at the cost of writing ripped audio to disk.
- Networking (improve on G64):
  - Client-authoritative movement is acceptable for a sandbox. Send compact state (position, facing or
    root rotation, action id, motion id plus frame plus speed, flags, ring count, sound events) at the
    tick rate as **unreliable** messages, with server rate limiting.
  - Remote clients run puppet instances (anim-only, as G64's fake Mario), with interpolation and short
    extrapolation.
  - Keep geometry streaming of the world physics mesh from the server (only the server has it).
  - Cache it client-side keyed by map name and CRC.
- Saving: ConVars and JSON config (character choice, colours/skins, keybinds); the collision cache in
  `data/gsa1/cache`. No disc-derived data is ever written unless the texture or audio cache option
  above is chosen.

### 8.7 Build and ABI checklist

- `libsa1`: either MSVC/clang-cl (simplest for a statically linked module) or MinGW behind a C ABI
  (G64's approach, which needed `dll2lib` and a second DLL). C11, warnings for pointer-size truncation,
  fixed-width types for every on-disc struct.
- Module: C++17/20, `gmod-module-base` (`GMOD_MODULE_OPEN/CLOSE`, `LUA_FUNCTION`, `ILuaBase`).
  `TargetName gmcl_gsa1_win64`. CI that builds the library and the module in one pipeline, so the
  released module source is never ahead of the public source (G64's v1.0.1 problem).
- Versioning handshake between the Lua addon and the module (G64's `GetLibVersion`/
  `GetPackageVersion`). The Lua must degrade gracefully when the module is missing: remote players
  should be shown with a GMod fallback model, not a sphere.
- Threading: if audio runs on its own thread, use a lock-free command queue from the game thread.
  Never touch `ILuaBase` off the main thread.

## 9. Quick reference: G64 numbers worth reusing

- Tick: 1/33 s (about 30.3 Hz), divided by `host_timescale`. Interpolation adds one tick of display
  latency.
- Scale: 2.5 SM64 units per Source unit (ConVar). Character render bounds are +/-160/S.
- Map cache: world cell 1000 HU, displacement cell 500 HU, +/-100 HU border margin. 32 convexes per
  server tick per player when streaming. Props processed at 8 per tick.
- Geometry buffer: 1024 triangles max per character, positions, normals and colours as 9 floats per
  triangle, UV as 6 floats.
- Network move packet: about 22 bytes at 30 Hz per Mario (reliable); relayed only to players with
  Mario inside their FOV.
- Texture atlas: Mario 704x64 RGBA inside a 1024x64 RT, so the U scale is 0.6875.

## 10. Open questions (for the G-SA1 effort)

1. Which GMod branch should be primary? G64 required the x86-64 beta. Is the default Windows branch
   still 32-bit in 2026? If yes, ship win32 too, which means `libsa1` must also be 32-bit clean (an
   easy win given the SH-4 origin).
2. Native mesh and texture creation (Source SDK interfaces through `garrysmod_common`) versus a
   Lua-only path. The native path is much faster but needs version-fragile engine headers; is that
   acceptable?
3. Is writing decoded textures or audio into `garrysmod/data` acceptable (local, user-derived), or
   must everything stay in memory, as G64 did?
4. Exact SA1 world-to-Source scale and handedness: calibrate from the Sonic model bounds and
   `Physics.ini` (`height=10`, `rad=4`).
5. SA1 logic rate (60 Hz vs 30 Hz) and how the original handles frame skipping. This affects the
   accumulator and the network rate.
6. Which characters and actions are in scope for v1? Sonic alone is the libsm64-like MVP; Tails,
   Knuckles and Gamma need extra systems (flight, glide/climb, lock-on targeting).
7. Where SA1 keeps each character's effect models, HUD textures and SFX bank on the disc (PRS names,
   MLT bank indices), and whether voice lines live in ADX/AFS. These need confirming against this
   repo's data research.
8. Whether SA1 land collision can work directly on arbitrary triangle soup (GMod maps), or needs a
   pre-pass to build SA1-style collision structures (bounding spheres per mesh, surface flags).
9. Licensing of the decompiled-code library and the addon. G64 left everything unlicensed and bundled
   GPL code; G-SA1 should pick explicit licenses and avoid GPL-incompatible bundling.
10. Anti-cheat and authority expectations for multiplayer (G64 trusted clients completely).
