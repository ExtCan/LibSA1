# SH-4 interpreter harness (`sa1h`)

A test oracle and development scaffold for the Sonic Adventure (DC) decompilation:

* **oracle** - run an *original* function from your own `baserom/1ST_READ.BIN` in an SH-4
  interpreter and the *decompiled* C (compiled natively for 32-bit x86) on identical memory and
  arguments, and compare return values, every byte of guest RAM and the hardware access stream;
* **scaffold** - decompiled C can call functions that are not decompiled yet (generated thunks run
  the original code in the interpreter), and original code can call into decompiled C (hooks /
  "routing"), so a subsystem can be ported function by function.

Nothing in here contains game code or data: the ROM is loaded at run time from `baserom/`, the
decoder table is generated from `tools/sh4/isa.py`, the native side from `src/1st_read/*.c`.

## Build

Requirements: Python 3.12 with `ziglang` (`py -3.12 -m ziglang`), the repository's generated
`build/1ST_READ.symbols.txt` and `build/1ST_READ.xrefs.json` (from `configure.py --split`), and
`baserom/1ST_READ.BIN` (+ `baserom/overlays/*.BIN`, `overlays.json` for `--overlay`).

```
py -3.12 harness/build.py                    # build/sa1h.exe: interpreter + every src/1st_read/*.c (matching code)
py -3.12 harness/build.py --non-matching     # build/sa1h_nm.exe: also the #ifdef NON_MATCHING bodies
py -3.12 harness/build.py --files none       # interpreter only (no native decompiled code)
py -3.12 harness/build.py --files src/1st_read/code_8C052A00.c src/1st_read/code_8C0A1120.c
py -3.12 harness/build.py --target win64     # build/sa1h64.exe: 64-bit, interpreter only
py -3.12 harness/build.py --target linux64   # cross-compile check (interpreter only, untested at run time)
py -3.12 harness/build.py --no-fma           # decompiled code without FMA contraction (see FP below)
py -3.12 harness/build.py --non-matching --pc        # build/sa1h_nm_pc.exe: the libsa1 configuration
py -3.12 harness/build.py --non-matching --pc --rt   # build/sa1h_nm_pc_rt.exe: + the libsa1 runtime natively
py -3.12 harness/build.py --files none --rt          # only the libsa1 runtime natively
py -3.12 harness/build.py ... --tag NAME             # private build/sa1h_NAME.exe (own gen_/obj_ directories)
py -3.12 harness/build.py --non-matching --pc --ga   # build/sa1h_ga.exe: the GUEST-ARENA lowering (tools/pclower.py)
```

`--pc` compiles the decompiled code with the one PC flag set of `tools/pc_cflags.txt` (the file libsa1 and
`tools/pclower.py` read too; `-DNON_MATCHING` from it applies only with `--non-matching`). `--rt` (implies
`--pc`) also compiles every `libsa1/src/rt/*.c` like a decompiled file (see "libsa1 runtime" below). Every
build compiles in `libsa1/src/rt/rt_fsca_q.c`, the FSCA table of the interpreter (generated by
`tools/dump_fsca.py`), so the `libsa1` directory must sit next to `sadc`.

`build.py` runs `tools/gen_optab.py` and `tools/gen_native.py`, compiles with zig (parallel,
incremental) and links. Decompiled files that do not compile or link at the moment (half-written
files of a running decompilation batch) are excluded and the build is retried, so the harness always
builds; the excluded files are listed at the end. The main target is **32-bit Windows** (`x86-windows-gnu`); after linking
the LARGE_ADDRESS_AWARE bit is set in the PE header (zig does not accept the linker flag), so the
process can map the Dreamcast RAM at `0x8C000000`. Everything goes to `harness/build/`
(`gen_<target>/` generated sources and `native_manifest.json`, `obj_<target>/` objects).

## Memory model

* Main RAM (16 MB) is one pagefile-backed section (`CreateFileMapping`) mapped with
  `MapViewOfFileEx` at `0x8C000000` (P1), `0x0C000000` (P0, overlays) and `0xAC000000` (P2), plus the
  area-3 mirrors `0x0D-0x0F`, `0x8D-0x8F`, `0xAD-0xAF` when the address space is free. All views alias,
  so guest address == host address and native code dereferences game pointers directly.
  `1ST_READ.BIN` is loaded at `0x8C010000`; `--overlay NAME` loads `baserom/overlays/NAME.BIN` at its
  `overlays.json` load address.
* The interpreter translates through a 4096-entry page table (1 MB pages): RAM and its mirrors in
  P0/P1/P2, VRAM (8 MB, `0xA4/0xA5..`, `0x84/0x85..`) and sound RAM (2 MB, `0xA08..`) as host buffers.
  P3 (`0xC0000000-0xDFFFFFFF`) is left unmapped on purpose (games do not use it; float garbage
  used as a pointer lands there).
* Everything else takes the slow path:
  * store queues `0xE0000000-0xE3FFFFFF` (writes buffered, `PREF` bursts them to
    `QACRn<<26 | addr`: into RAM/VRAM, or to the io callback, e.g. the TA FIFO);
  * hardware (Holly/PVR/G1/G2 `0x005Fxxxx`, AICA `0x0070xxxx`, RTC, TA FIFO `0x10000000-`, boot ROM,
    flash, P4 control registers `0xFFxxxxxx` and cache arrays): `sh4_set_io()` callback, logged in
    the event log. Default: log + return 0, except P4 registers which read back the last value
    written. `sh4_strict_io` (used by `diff` and `boot`) limits "hardware" to the register windows
    games really use, so wild pointers fault;
  * NULL page (`0x0000-0xFFFF`): reads return 0 (the boot ROM would be there), writes are ignored,
    counted in `sh4_null_touched` (`sh4_null_page_faults=1` makes them fault);
  * host pass-through (32-bit host only): guest accesses to the current thread's stack (read/write)
    and to the exe image (read only) go to host memory. This is how a guest callee reads the native
    caller's stack locals and string literals. `sh4_host_passthrough`: 0 off, 1 any committed host
    memory, 2 (default) stack + image;
  * anything else: `SH4_FAULT_MEM`.
* The interpreter keeps a 4 KB dirty map of RAM writes (`sh4_ram_dirty`), used to restore RAM cheaply.

## Interpreter

* Decoding: `sh4_optab[65536]` maps every word to one of 209 instruction forms; it is generated
  from `tools/sh4/isa.py` (validated against asmsh), so the interpreter accepts exactly what the
  project's disassembler decodes (59,001 valid encodings). Each handler extracts its fields.
* Integer: the complete SH-4 set incl. DIV0S/DIV0U/DIV1 (manual algorithm), MAC.L/MAC.W with S-bit
  saturation, DMULS/DMULU, SHAD/SHLD, ROTCL/ROTCR, CMP/STR, TAS.B, XTRCT, SWAP, GBR logic ops,
  banked R0-R7 (SR.RB, LDC/STC Rn_BANK), privileged LDC/STC/RTE/LDTLB, PREF (store queues),
  OCBI/OCBP/OCBWB (no-ops), MOVCA.L, TRAPA/SLEEP (handler or fault). `MOV.x @Rm+,Rm` does not
  increment; `MOV.L Rm,@-Rm` stores the original value.
* Delay slots: the branch target (and PR for BSR/JSR/BSRF) is computed first, then the slot runs,
  then the jump; BT/S and BF/S sample T before the slot. Branches, TRAPA, LDC and PC-relative
  loads in a slot fault (`SH4_FAULT_SLOT`). No interrupts, exceptions, MMU or caches are modelled.
* FPU: FR/XF banks (FPSCR.FR, FRCHG), SZ=1 pair moves (`FMOV DRn/XDn`, even register <-> lower
  address in little-endian mode), PR=1 double arithmetic (FADD/FSUB/FMUL/FDIV/FSQRT/FCMP/FLOAT/FTRC,
  FCNVSD/FCNVDS, FABS/FNEG on DRn), FLDS/FSTS/FLDI0/FLDI1, LDS/STS FPSCR/FPUL. NaN results are the
  SH-4 default qNaN `0x7FBFFFFF`. FPSCR flag/cause/enable bits are not maintained.

### Floating point accuracy

| Operation | Method | Exact? |
|---|---|---|
| FADD FSUB FMUL FDIV FSQRT FLOAT FCMP | host SSE in the FPSCR mode: MXCSR RC=toward zero when RM=1, FTZ+DAZ when DN=1 (set on every FPSCR write and at depth-0 calls) | yes (IEEE in the same rounding mode; denormal inputs/outputs flushed like DN=1) |
| FMAC | product in double (exact), one double add, cvt to float; under RZ nested truncation equals the directly truncated exact result | yes under RZ (FMAC is treated as fused, which x86 FMA3 confirms: see diff results) |
| FTRC | truncation with SH-4 saturation (>= 2^31 -> 0x7FFFFFFF, < -2^31 -> 0x80000000, NaN -> 0x80000000) | yes |
| FIPR, FTRV | products and sum in double, rounded once | **approximate** (hardware internal precision differs in the last bits) |
| FSRRA | 1/sqrt in double, rounded | **approximate** (hardware ~2^-21) |
| FSCA | table of sin((angle & 0xFFFF) * 2pi/65536) rounded to nearest, exact 0/+-1 at quadrants, exact quadrant symmetry; FR[n]=sin, FR[n+1]=cos. Since 2026-10-20 the quarter wave is loaded from `libsa1/src/rt/rt_fsca_q.c` (generated from `fsca_build()`, which used to run at start-up and depends on the C library's `sin`); `selftest` checks the two are identical | **approximate** (hardware table) |

The models live in `include/pc/sh4_fpmodel.h` and are shared verbatim with the libsa1 runtime, so native
runtime code and the interpreter compute the same bits (`docs/libsa1_integration.md` 8.2).

Choice for round-to-zero: the host FPU is switched to RZ+FTZ+DAZ (`sh4_host_fp_game_mode()`, the
harness process runs in the game's mode all the time). Limits: x86 decides "tiny" for FTZ after
rounding, the SH-4 before (results within one ulp of FLT_MIN may flush differently); RM=2/3
(reserved) are treated as RZ; the host C library (printf, sin) also runs in RZ.

## Calls, hooks, native glue

* `sh4_call(addr, args[4], fargs[8])` / `sh4_invoke(addr, sh4_arg[], n, &r0, &fr0)`: SHC ABI - ints
  and pointers in R4-R7, floats in FR4-FR11, the rest on the stack in declaration order (verified by
  compiling probes with SHC 5.1r03; variadic calls put every argument on the stack:
  `sh4_invoke_varargs`; struct arguments/returns are not supported). R15 = `SH4.stack_top` (default:
  the game's own stack top `0x8C00F400`) for depth-0 calls, the current R15 for nested ones;
  PR = `SH4_SENTINEL` (`0xDEADBEE0`); returns R0/FR0. Re-entrant: a hook or native function may call
  back into the guest. `sh4_call_regs(addr)` runs with the registers as set (non-ABI helpers).
* Faults (`SH4_FAULT_*`) longjmp to the innermost `SH4_TRY` guard (or the depth-0 call); inside a
  guard, access violations / divide errors in *native* code are caught too (vectored exception
  handler -> `SH4_FAULT_NATIVE`). `SH4.ilimit` bounds the instruction count.
* Hooks: `sh4_hook_add(addr, fn, user, name)` - when guest control reaches `addr` (call, jump or tail
  call) `fn(cpu)` runs and execution continues at PR. `sh4_hle_ret0/ret1/retu` stubs; hook calls can
  be recorded in the event log.
* Native decompiled code (32-bit Windows build): `tools/gen_native.py` parses each
  `src/1st_read/*.c` with clang (`zig cc -Xclang -ast-dump=json`) and generates
  * **absolute symbols** for every referenced `D_/B_/named` data symbol
    (`.set _D_8C1BEF54, 0x8C1BEF54` in `native_abs.c`, from `build/1ST_READ.symbols.txt`);
  * a **thunk** per referenced function that is not compiled natively (incl. `ASM_STUB`s and
    implicitly declared functions): marshals its typed arguments to the SHC ABI and runs the original
    via `sh4_invoke` (`native_thunks.c`). Files that declare the same function with different
    prototypes get separate thunks (renamed by a `#define` in that file);
  * an **adapter** per natively defined function: guest registers -> native call -> R0/FR0
    (`native_registry.c`, table `sh4_native_fns` with guest address and signature);
  * a **rewritten copy** of each source (`native_src/`): every decimal float literal becomes the hex
    float of its round-toward-zero single value (SHC `-round=zero -fpu=single`: clang would round to
    nearest and make unsuffixed literals double); the manifest lists literals where this matters.
  Decompiled files are compiled with `-O2 -msse2 -mfpmath=sse -mfma -ffp-contract=on -frounding-math
  -fno-strict-aliasing -fwrapv -fno-builtin` and `-include harness_pre.h` (with `--pc`: the flags of
  `tools/pc_cflags.txt`, i.e. no contraction, `-DTARGET_PC`).
* `sh4_route_native(1)` (`call --route`, `nativetest`): guest calls of an address that has a native
  implementation run the native code (hook with the adapter). Off by default (pure original).
* Function pointers across the boundary: a native function pointer stored in guest memory and
  called by guest code is recognised (thunk -> its original; native function -> adapter, or the
  original when routing is off). Native code calling a *guest* address (e.g. `tp->exec(tp)` with
  `exec = 0x8C0A77BC`) hits a DEP execute fault (guest RAM is not executable); the vectored handler
  redirects to an asm trampoline that runs the guest function with the signature from the thunk table
  (four integer arguments when unknown) and returns R0 in EAX or FR0 in ST(0).
## libsa1 runtime in the harness (`--rt`)

`build.py --pc --rt` passes every `libsa1/src/rt/*.c` (except the FSCA table, which every build compiles as a
harness source) to `gen_native.py` like a decompiled file (`--inc libsa1/src/rt` for `rt.h`). Their
functions are named like the SDK symbols (`njSin`, `func_8C63A9DC`), so they are registered at the SDK
addresses of `build/1ST_READ.symbols.txt` and get adapters:

* `diff njSin 2000 1 --ulps 0` compares the runtime C with the original SDK code (`PASS` = bit-identical);
* `--route` (trace, call) hooks them at their SDK addresses, and the decompiled code calls them directly
  instead of a thunk to the original, so `regress.py --route` checks game code and runtime together;
  `--files none --rt` routes the runtime alone into the interpreted game;
* runtime code reaches XMTRX as `SA1_XMTRX` (`libsa1/src/rt/rt.h`), which in the harness is the
  interpreter's XF bank (`sa1h_xmtrx = SH4.xf.f`, `sh4_intrin.c`), so native runtime and original SDK
  code can alternate on one matrix state; `TARGET_PC_HARNESS` (from `harness_pre.h`) selects that profile.

Rules for runtime code and the verification loop: `libsa1/src/rt/README.md`. First file: `rt_trig.c`
(njSin, njCos, njTan, njSqrt: `diff` PASS with `--ulps 0`; the 10 traces identical with everything routed).

## GUEST-ARENA build (`--ga`)

`build.py --non-matching --pc --ga` builds `build/sa1h_ga.exe` (with `--tag T`: `build/sa1h_T.exe`) from the
GUEST-ARENA lowering of the decompiled code instead of the sources (`docs/libsa1_integration.md` 2.3, rung V1):

1. `tools/pclower.py --profile ga32 --extern-unresolved --drop-failing` lowers every `src/1st_read/*.c` into
   `build/gen_<tag>/pclower/` (profile ga32: identity decode, guest == host at `0x8C000000`, so the lowered code
   works on the interpreter's RAM);
2. `harness/tools/gen_ga.py` writes the glue into `build/gen_<tag>/`: `ga_src/` (the lowered TUs, with `#define`s to
   per-signature thunk variants where TUs disagree about an external prototype), `native_thunks.c` (one thunk per
   external function), `native_registry.c` (adapters at the DC addresses, so `--route`, `--route-only`, `list`,
   `route_matrix.py` and `diff` work as for the plain build), `sa1g_fntab.c` (code map, `-DSA1G_FN_HOST`),
   `sa1g_pcdata.c` (R4 pcdata units in static storage), `ga_glue.c` (`sa1_fn`, the GA fault entry points, the
   intrinsic forwarders to `sh4_intrin.c`, `sa1_rt_xmtrx` = the XF bank, `sa1_tmu` of `pc_runtime.c` exported as
   pcdata) and `ga_manifest.json`;
3. the lowered TUs compile with the flags of `tools/pc_cflags.txt` plus `-DSA1_GA32` (no `harness_pre.h`), the
   glue with the harness flags; everything links with the interpreter as usual.

Indirect calls in lowered code are `sa1_fn(g, sig)`, which returns the DC code address itself: the call takes the
same DEP fault as an unlowered native call through a guest function pointer, and `sh4_call.c` runs the routed
native function or the original. Function pointers in memory are therefore always DC addresses in this build.
`--rt` adds the lowered `libsa1/src/rt` (its `sa1_tmu` / `sa1_tmu_tcnt1` replace those of `pc_runtime.c`;
`rt_input.c` stays with the interpreter: its libsa1 profile reads the world's pad latch `sa1_rt_pad`).

```
py -3.12 harness/build.py --non-matching --pc --ga                          # build/sa1h_ga.exe (about 5 min)
py -3.12 harness/tests/sim/regress.py --route --exe harness/build/sa1h_ga.exe
py -3.12 harness/tools/route_matrix.py --exe harness/build/sa1h_ga.exe --out build/pclower/v1/route_matrix_ga.json
py -3.12 tools/pclower.py --selftest                                       # the rule tests (ga32 + ga64 runs)
```

A TU that pclower cannot lower is left to the interpreter (`report.json` `dropped_units` in the pclower directory),
and one that needs a runtime piece the harness lacks (e.g. `UNK_PcWrite`) is excluded by `gen_ga.py`
(`ga_manifest.json` `excluded`), like `gen_native.py` excludes unresolved files.

## Overlay images and the image guard

Overlays that share a load slot reuse DC code addresses: STGxx, B_CHAOS7, MINICART, ADV02, ... all load at
`0x0C900000`, and `0C914D60` is Super Sonic's trigger in B_CHAOS7 but a 6-byte `FreeTask` wrapper in MINICART
(B_CHAOS7 entries that are also function entries elsewhere: `0C900480` B_EGM3, `0C9004D4` STG05, `0C914D60`
ADV02 and MINICART, `0C91514A` MINICART). Decompiled overlay C (`src/overlays/<dir>/*.c`) is built into the
harness like 1ST_READ C, with three additions:

* **Names.** As `tools/pclower.py` does, a function an overlay file defines, or references inside its image's
  code range, is `<IMAGE>__<name>` (`B_CHAOS7__func_0C900480`; `gen_native.py` adds `#define`s to the native
  copy, pclower renames in `--ga` builds). A 1ST_READ call of `func_0C900480` therefore stays a thunk into the
  interpreter, and two images may define the same address.
* **Tables.** The registry (`native_registry.c`) records the image of every native function
  (`sa1h_native_fn_image[]`) and, per image, the code ranges of `config/overlays/<dir>.yaml` and the CRC-32 of
  those bytes in `baserom/overlays/<DIR>.BIN` (`sa1h_fn_images[]`, `src/image_guard.h`;
  `native_manifest.json` / `ga_manifest.json` `images`).
* **The guard (trace).** After the routing set-up, every routed overlay function loses its routing hook to a
  guard hook: the native function runs only while the CRC-32 of the same ranges in guest RAM equals the
  image's (identified once per guard epoch: every logic step, every file the GD-ROM HLE reads or closes,
  every set-up phase), and the original runs otherwise. Calls through a function pointer from native code
  (the DEP path of `sh4_call.c`) are no longer "routed" and come back through the interpreter to the same hook;
  several images may share one address. `trace --no-image-guard` keeps the plain routing hooks (route by
  address, whatever image is loaded): the negative control. At the end the trace prints, per image, the
  guarded addresses, native calls, calls left to the original and the addresses reached, e.g.
  `sim: image guard B_CHAOS7: 25 guarded addresses (12 reached), 2386 native calls, 0 calls left to the
  original (another image loaded), image seen`.

Only `trace` applies the guard; `call --route` and `nativetest` route by address (load the right overlay with
`--overlay`). The stage image of a trace header (`stage_crc32` / `stage_size`) is now the overlay the stage
load put at `0x0C900000`, found by name among the files the GD-ROM HLE read (`B_CHAOS7` for level 19, `ADV02`,
`MINICART`, ...; `STGnn` as before for levels 0-12).

    manager task resets the whole array in its first exec (8C091016 -> 8C0916AE / 8C0916EE; with `--no-objects`

    conditions again right after that reset (a one-shot hook on 8C091016). A libsa1 world has no SET manager: its

  * `+ocp=HEX` (round 0.9.4, `docs/research/gsa1_094_plan.md` 6.4 with its Review R.7): the same `OBJ_CONDITION` with

## Host objects: the round-5 oracle (`--hostobj`, `NAME.obj.bin`)

`docs/research/gsa1_rounds_plan.md` 9.4, `docs/libsa1_interaction.md` 4.3 and its addendum (6.7). libsa1's host-object
layer (its proxies are real game tasks built like SA1 enemies, whose exec is libsa1's code at the synthetic address
`0x7F000100`) is checked against the original game by running **libsa1's own layer on the original code**:

* **The layer, unchanged.** Every 32-bit Windows build compiles `libsa1/src/sa1_hostobj.c` (the registry and the
  public calls) and `libsa1/src/world/sa1_world_hostobj.c` (the proxies, the `LIBSA1_HOST` exec, the pre / post hooks)
  with libsa1's world FP flags, `-DSA1_GA32` (guest == host), and three renames that keep them off the GUEST-ARENA glue
  of `--ga` builds (`sa1_fn`, `sa1g_sqrtf`, `sa1g_fsca` -> `sa1h_ho_*`). `src/ho_lib_glue.c` gives them their world:
  the arena is the harness's DC RAM, the extension segment `0x18` is 1 MB of host memory mapped at its guest address
  `0x98000000` (`sh4_map_extra`: in the page table and at that host address, so the game code, interpreted or native,
  reads the OBJ_CONDITION stand-ins and the CCL templates where libsa1's game code reads them), the context has libsa1's
  default coordinates (the Source preset) and the character is id 1; it copies the few small libsa1 functions the two
  files call (`sa1g_sqrtf` / `sa1g_fsca` on `include/pc/sh4_fpmodel.h`, `sa1g_world_event_push`, `sa1_fail`,
  `sa1_copy_out`, `sa1_to_host_*`).
* **The game functions it calls** (CreateElementalTask, FreeTask, CCL_Init / CCL_Entry, the enemy initialiser 8C047040,
  the movable set-up 8C0586A0, the damage check 8C0489E4, the bounce 8C048980, score, rings, the death request, the
  spring request 8C07C720, SetVelocityP, E-102's marker release 8C0D5D90 and time bonus 8C0D5064, the six drop functions,
  atan2f 8C10D0F8) are typed cdecl wrappers in `src/ho_oracle.c` that run them with `sh4_invoke`: the original code in
  the interpreter, or the routed native code with `--route`.
* **Where it runs.** As libsa1's step `sa1g_step_game`: `pre` at the entry of the task executor `8C0988A4` (after the
  pad update of the asm-only `8C04E714`), `post` right after the CCL pass `8C0342E0` (hooks that chain to the routing
  hooks they replace). The proxies' exec `0x7F000100` is a special hook (`sh4_special_hook_add`, `src/sh4_call.c`): an
  interpreted JSR runs it like a RAM hook, and a native call through the task's exec pointer (a routed or lowered
  executor; the DEP / access-violation path) jumps to the layer's native exec.

The script (`tests/sim/ho/NAME.ho`; one call per line, made before logic step STEP; SA1 positions and lengths, converted
to the Source preset's host space: `host = 4 * (x, -z, y)`):

```
STEP add H KIND [pos=X,Y,Z] [yaw=R] [flags=F|F..] [armor=N] [touch=N] [cooldown=N] [launch=V] [reach=R] shape=S ...
     KIND ENEMY TARGET BREAKABLE HAZARD HOLDABLE BALLOON;  S sphere:R | cyl:R,HALFH | box:HX,HY,HZ [@CX,CY,CZ] [^YAW] [!OFF..]
STEP update H ...   STEP move H X,Y,Z [YAW]   STEP remove H KILLED|SILENT   STEP release H   STEP rings N   STEP mask 0xN
STEP damage [face=X,Y,Z] [kill] [obj=H]   STEP option NO_DEATH|KEEP_RINGS|NO_DAMAGE 0|1   STEP config [window=N] ..
```

`--create-task ADDR[:IM[:LIST]]@X,Y,Z[,ANGY]` also places the task (taskwk pos and ang.y after CreateElementalTask): a
real SA1 object for a reference (O_SAMPLE_S, a ground spring). Each step's calls, the host-object events
(`sa1_poll_hostobj_events`, host space, polled in the host's default FP mode as a libsa1 host polls them), the layer's
world events (HURT, DEATH, CAPACITY), the held state (`sa1_character_held`), the proxies (taskwk pos / flag / mode,
colliwk flag, enemy work `+0x4E`) and the `--create-task` tasks (handle `0x80 + k`) go to `NAME.obj.bin`
(`sa1_trace_ext.h`: `sa1_trace_obj_header`, 280 bytes, then one 1,736-byte `sa1_trace_obj_rec` per step). `--check`
compares it (the proxies' guest addresses aside); `sa1trace.py obj NAME.bin [--all]` prints it and `diff` compares it.

**Version 2** (round 0.9.2): a run whose `--create-task` tasks use `/SX,SY,SZ`, `+ocp` or `+late` writes version 2:
the version-1 header (unchanged, `version` 2, `header_size` 424), one `sa1_trace_obj_task_ext` per task (flags, scale,
condition slot and range; round 0.9.4: with `+ocp=HEX` the flag `SA1_TOBJ_T_OCPW` and the initial ssCondition in
`reserved[0]`, which `sa1trace.py` prints as `ocp SLOT=WORD`), and records of 1,768 bytes: the version-1 record followed by `sa1_trace_obj_rec_ext`, the
word 0 of each task's `OBJ_CONDITION` after the step (scCount | scUserFlag << 8 | ssCondition << 16: the game's own
"collected" signal of a RING, 8C091BA4, and a ring group's taken bits, 8C087EAC -> 8C091C00). Every other run still
writes version 1, byte for byte as before; `--check`, `sa1trace.py` and LIB's `tests/world_replay.c` read both (the
replay makes the scale and the condition, and compares the condition words like the records). A `--create-task` task
that has ended (seen live, then freed or `DestroyTask`) is reported as gone from then on: its freed task block may be
reused by another task (the item box's after step 44), whose state is not this task's.

**libsa1 replays them through the public API** (`libsa1/tests/world_replay.c`, `tests/build_replay.py` list `HOSTOBJ`):
the replay's character gets a fresh registry and the sidecar's tasks (made in the world after the boot), the record's
calls are made before each step (`sa1_hostobj_add` ... `sa1_character_damage`, `sa1_character_set_option`,
`sa1_character_add_rings`), and the world's own sidecar is written next to its trace for `sa1trace.py diff`: strict
like the trace (V6, V5 reseeded, DISC, V7 x86 = x64).

## Differential test (`diff`)

Per function and iteration (deterministic in the seed):

1. restore the baseline RAM image (the loaded ROM, or with `--warm` the state after the game's own
   matrix/view init, heap init, task system init, player loader and two logic frames - see `boot`);
2. inputs: a 64 KB scratch area (`0x8CF00000`) of random structured words (scratch pointers, small
   integers, floats, 0); every other iteration random values in the BSS variables that the
   function's source file references; arguments per the signature (pointers into the scratch area,
   mostly small integers, floats in +-1000 and specials) or `--args`;
3. run the original with `sh4_invoke` (pure: no routing), record R0/FR0, fault status, RAM, the
   hardware/store-queue event log;
4. restore the inputs, run the native function through its adapter with the same guest registers
   (callees reached through thunks run the same original code in the interpreter, so a Ninja draw
   call is compared by the TA data it writes);
5. compare: return value (per declared type, code pointers canonicalised), every RAM word, the event
   sequence.

Not counted as differences: the guest stack area (frames differ by design), saved guest stack
addresses, a native function/thunk address where the original stored the guest address, a return
address where the native side has `SH4_SENTINEL`, NaN vs NaN (SH-4 `7FBFFFFF` vs x86 `FFC00000`:
"approx"), floats within `--ulps` (default 4: "approx").

"Inconclusive" iterations: both sides faulted; the original faulted on a wild/misaligned pointer or
ran out of budget (`--budget`, default 4M instructions; two timeouts end the function early); the
native side dereferenced NULL where the original read the (zero) boot ROM area; the native side hit
a wild non-RAM address where the original accessed "hardware". The host stack below the native
call is zeroed before each run, like the restored guest stack, so uninitialised locals read the
same zeros where possible. Verdicts: `PASS` (all conclusive iterations exact), `APPROX`, `FAIL`,
`FAULT` (no conclusive iteration), `SKIP` (no adapter: unsupported signature). `diff all` runs one
child process per source file (a native function that smashes its own stack only takes its child
down; the rest of that file is then tested one function per process, `CRASH` lines). Native code
has no instruction budget, so each child also gets a wall-clock limit (`--child-timeout`, default
120 s): a file that runs over is retested function by function, and a function that never returns
is reported as `HANG`.

## Headless boot (`boot`)

`sa1h boot [frames] [character] [level]` runs, on the bare ROM image: `func_8C0544E2` (njInitMatrix
+ screen/view setup), heap init `8C098A10`, task system init `8C09844A`, the game's player loader
`8C04F3C0` (`CreateElementalTask(7,1,main)` -> Sonic main `8C0A77BC` for character 0), then per frame
the 60 Hz logic step `8C04E714` (input, task executor `8C0988A4`, collision, ...) and with `--disp`
the display pass `8C0988C4`. `--init` first runs the full SDK/game init `8C053AC0`. Each step runs
under an auto-stub loop: on a fault, the innermost SDK function on a shadow call stack (or else the
innermost function) gets a "return 0" hook, RAM is restored and the step retried; the list of
stubs is the report. `--stick X,Y` / `--buttons M` install a `pdGetPeripheral` (`8C601F5A`) HLE that
returns a standard controller on port 0. BIOS syscall vectors (`8C0000B0..E0`) are stubbed.

## Reference simulator (`trace`)

Full description: `docs/harness_simulator.md`. In short: `trace` runs, all in the interpreter, the
game init `8C053AC0`, the character select `8C04F5F4` (loads `S_MOT.PRS` at `0x0CC00000`), the stage
load `8C04E490` (stage PRS -> `0x0C900000` through the game's own PRS decoder, SET/CAM files, landtable
sphere init) and the stage start `8C04E660` (camera, landtable manager task `8C0519C0`, player via
`LoadPlayerTask` + start position `8C04F8FA`, death zones, CCL), then per display frame `8C04E95A`
(2 logic steps `8C04E714` each). HLE: GD-ROM file system (gdFs* read the user's `disc/SONICADV/`
files), pdGetPeripheral (scripted pad), vsync waits, the view part of njInitSystem `8C604702` (the
640 x 480 screen and njInitView, so the game's visibility test `8C038D00` works: the default since
2026-10-20, `--no-screen` for the old zero screen; trace header flag 8), TMU timers, maple server, sound
handshake, voice AFS, the land strip and model renderers. Each logic step is wrapped by a hook that applies the
script's pad state and records taskwk/motionwk/playerwk/csts (decoded + raw) and the input as the player code
sees it. Functions whose C describes a private register convention with assembly-only callers (the sprite module
`8C09E880` / `8C09EB08` / `8C09EE44`) are never routed (`gen_native.py` `NO_ROUTE`).

```
sa1h trace --level 1 --act 0 --no-objects --input "30 0 0; 120 0 -127; 1 0 -127 A; 60 0 -127"
  step   30: in (   0,-127,0000) mode   2 act   9 pos (   -9.0362     3.9976     4.0342) ... attr A0100001 land 18
  step  150: in (   0,-127,0004) mode   8 act  14 pos ( -159.5175     3.5685    83.0695) ... attr 00000000 land 20
```

Runs are deterministic (`--check REF.bin`: every record byte but the instruction count). With
`--route` the natively compiled decompiled functions replace the originals inside the simulation, so
a whole-game trace validates the decompiled C; `tools/route_bisect.py` narrows a divergence to one
function.

## Limits and platform differences

* Native decompiled code needs the 32-bit Windows build (guest RAM at its DC addresses). The
  64-bit and Linux builds are interpreter-only; the Linux build is only compile-tested.
* Signatures the generator cannot marshal (struct by value, `long long`) get a thunk that faults;
  variadic thunks forward the named arguments plus 8 stack words (floats are promoted to double by
  the native caller); unprototyped/implicit declarations pass 4 integer words.
* Float -> int conversion of values >= 2^31: SH-4 FTRC saturates to `0x7FFFFFFF`, x86 gives
  `0x80000000` (seen in `func_8C0897F8` with random inputs); a port that needs it must use a
  saturating cast.
* x86 tolerates misaligned and NULL-page accesses differently (misaligned: native fine, SH-4
  address error; NULL page: native crash, DC reads the boot ROM). The diff classifies these
  iterations as inconclusive.
* Uninitialised locals (legal in the original binary) differ natively: register/stack garbage.
* NaN payloads differ (x86 produces `FFC00000`, SH-4 `7FBFFFFF`).
* FIPR, FTRV, FSRRA, FSCA are approximations of the hardware (see the table above).
* No interrupts, timers, DMA, MMU, cache, exceptions; hardware registers only read back latched P4
  values or 0; code that waits for vblank/GD-ROM/maple spins until the budget runs out (stub it).
* Native code that writes through a wild pointer can corrupt the harness (pass-through is limited to
  the host stack and exe image; RAM is restored after every iteration).

## Findings for the decompilation

* (reference simulator, `--route`) FP contraction must follow SHC per expression: `func_8C027360`
  (triangle-edge cross product, land collision) is `FMUL, FMUL, FSUB` in the original, but with
  `-mfma -ffp-contract=on` clang fuses `a*b - c*d`, so the floor normal of a run differed by one ulp
  at step 95 (the function has since moved under NON_MATCHING; NON_MATCHING `PSetPosition` does the
  same; both are exact with `--no-fma`); building everything without FMA diverges at step 4 instead
  (functions where SHC emitted FMAC). The PC build needs `-ffp-contract=off` plus explicit
  fused operations where the original has `FMAC`.
* (NON_MATCHING, simulator) `func_8C02D2E0` / `func_8C02D410` (`code_8C02D060.c`) write other shadow
  fields than the original (`playerwk.shadow.angz` `0x80000000` vs 0, `Attr_bottom`); `func_8C02D278`
  takes and returns its vector in `FR4-FR6` (`FIPR`/`FSRRA` helper), not through a pointer, so its
  C prototype and routed adapter are wrong.
* `include/sa1/engine.h` defines `GetStageNumber` as itself, which undid gen_native's per-file renames
  of conflicting prototypes (link error); gen_native now re-applies them after the last `#include`.

* `8C63A970` returns FR1 of FSCA (cosine) and `8C63A9B8` FR0 (sine): `8C63A970` is njCos and
  `8C63A9B8` njSin, the opposite of `docs/research/sa1_code_map.md` section 5.1 (and of the comment
  in `code_8C014A78.c`).
* Conflicting extern prototypes across files (see `native_manifest.json`, `signature_conflicts`):
  `func_8C608C82` is `void` in `code_8C014480.c` but returns `Sint32` in `code_8C082A60.c` (the
  original returns a status), `func_8C015820`, `func_8C04F7E0`, `func_8C0509B8`, `func_8C0509DA`,
  `func_8C07C65E`, `func_8C07C676`, `func_8C07CFA0`, `func_8C07CFDE` (9 in matching code, 24 with
  NON_MATCHING).
* 104 float literals in the matching sources round differently under clang's default
  round-to-nearest (and unsuffixed literals would be double): the native build rewrites them.
* NON_MATCHING bodies that do not behave like the original: `func_8C0112E6` (no return value),
  `func_8C08AFFA`, `func_8C088000`, `func_8C010340`, `func_8C0826B0`/`func_8C085F4C` (~10 ulps),
  `func_8C08925A` (stack overflow on large n), and the `func_8C085ABA..AE6` octant tails, which take
  their input in R2 (not an ABI register), so they cannot be compared as C functions.
  `code_8C0103C4.c` (`xm`) and `code_8C012520.c` (`UNK_PcWrite`) reference undefined names under
  NON_MATCHING.
